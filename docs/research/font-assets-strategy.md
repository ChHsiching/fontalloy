# Font asset strategy

Research date: 2026-10-10. Scope: how FontAlloy should store/fetch the ~81 bundled font families (~375 MB of TTF/OTF) in the repo, and how the Tauri 2 app delivers them at runtime for glyph previews (and for the fontTools sidecar, which needs the same files on disk).

## Question

Best practice for (a) storing/fetching the font binaries in the project and git repo, and (b) delivering them to the Tauri app at runtime — weighed against install size, offline use, repo clone size, license compliance, and the fact that font preview quality IS the product.

## Findings

### Tauri 2 resources and webview access

1. `tauri.conf.json > bundle.resources` accepts a list or a map of source→target paths; glob patterns are supported; a list entry like `dir/` recursively copies preserving structure, `dir/**/*` copies files recursively, and with the map form "the original directory structure is not preserved" (everything is copied into the target directory). Relative `..` is rewritten to `_up_`. Source: https://tauri.app/reference/config/ and https://tauri.app/develop/resources/

2. At runtime the resource root is resolved with `resourceDir()` / `resolveResource('rel/path')`. Platform locations: Windows — the directory containing the main executable; Linux — `/usr/lib/<exe>` (AppImage: `${APPDIR}/usr/lib/<exe>`); macOS — `${exe_dir}/../Resources` inside the .app. The docs warn the exact path "is not a contract and things might change in the future". Source: https://tauri.app/reference/javascript/api/namespacepath/

3. The webview can read resource files as binaries through the fs plugin: `readFile(path, { baseDir: BaseDirectory.Resources })` returns binary data; the required permission set includes `fs:allow-read-text-file`/`fs:allow-read-file` plus `fs:allow-resource-read-recursive` ("full recursive read access to the complete $RESOURCE folder"). On Linux and macOS there is no write access to `$RESOURCES`; on Windows a perMachine install needs admin to write there — read-only use is the supported pattern. Source: https://tauri.app/plugin/file-system/ and https://tauri.app/develop/resources/

4. Alternatively the webview can load disk files by URL via `convertFileSrc(filePath)` ("Convert a device file path to a URL that can be loaded by the webview"). Requirements: the asset protocol must be enabled with the files in its scope (`assetProtocol: { enable: true, scope: [...] }`) and the protocol origins must be allowed in `app.security.csp` (example CSP includes both `asset:` and `http://asset.localhost`, the Windows form). Source: https://tauri.app/reference/javascript/api/namespacecore/

5. The asset protocol responds with `Access-Control-Allow-Origin: <window origin>` on every response (including errors), so cross-origin CSS `@font-face url(convertFileSrc(...))` from the webview origin is permitted; range requests are also handled (`Access-Control-Expose-Headers: content-range`). Source: `crates/tauri/src/protocol/asset.rs` in the Tauri repo, https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri/src/protocol/asset.rs (lines 24, 42, 102 at time of writing).

6. The asset protocol's Content-Type is derived from `MimeType::parse(magic_buf, path)`; Tauri's mime module has no `ttf`/`otf`/`woff` mappings and falls back to `application/octet-stream`. Browsers do not require a font-specific MIME type for `@font-face`, but that is browser behavior, not a documented contract — the `FontFace(arrayBuffer)` path (which FontAlloy's prototype already uses for user-local fonts) sidesteps the question entirely. Source: https://raw.githubusercontent.com/tauri-apps/tauri/dev/crates/tauri-utils/src/mime_type.rs

7. Installer-size implications: `resources` entries are copied into every bundle the Tauri bundler produces, so ~375 MB of fonts grows every installer (NSIS/MSI/deb/AppImage/dmg) and every app update payload by roughly that order (font binaries compress imperfectly; the nerd-fonts project ships parallel `.tar.xz` because xz is smaller, indicating meaningful but not total compression). The mechanism (resources are embedded in all bundles) is documented; exact compression ratios are not. Source: https://tauri.app/develop/resources/

### Git/GitHub strategies for large binaries

8. Normal git objects: GitHub warns on files over 50 MiB and "blocks files larger than 100 MiB"; repositories should ideally stay under 1 GB ("less than 5 GB is strongly recommended"). Committing 375 MB of fonts (5–25 MB per file, all under the per-file limit) is therefore allowed but directly against the documented size guidance, and history bloats permanently because binaries do not delta well. Source: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github

9. Git LFS billing (2026 state): "Previously, Git LFS billing used pre-paid data packs. These have been removed and replaced with metered billing and you only pay for what you actually use." Included amounts: GitHub Free/Pro/Free-for-organizations — 10 GiB bandwidth + 10 GiB storage per cycle; Team/Enterprise Cloud — 250 GiB + 250 GiB. Bandwidth is "billed per GiB downloaded" and includes every clone/fork/Actions fetch of LFS objects; "usage is always measured against the repository owner's account" — public repositories get no exemption. If the spending budget is $0 (or no payment method), further LFS downloads are blocked for the rest of the month. Per-file LFS object caps: 2 GB (Free/Pro), 4 GB (Team), 5 GB (Enterprise). A 375 MB catalog exhausts the free 10 GiB/month after ~27 full clones; this makes LFS structurally wrong for a popular open-source catalog. Sources: https://docs.github.com/en/billing/managing-billing-for-git-large-file-storage/about-billing-for-git-large-file-storage and https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage

10. GitHub Releases as an asset store: "Up to 1000 release assets may be associated with a single release. Each file included in a release must be under 2 GiB. There is no limit on the total size of a release, nor bandwidth usage." Release assets have a stable documented public URL (`browser_download_url`, i.e. `github.com/owner/repo/releases/download/<tag>/<file>`); the REST API documents downloading asset content either by fetching `browser_download_url` or by `Accept: application/octet-stream` (handling "both a 200 or 302 response"). Fonts of 5–25 MB fit the per-file limit by two orders of magnitude; 81 families fit the 1000-asset cap trivially. Sources: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases and https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28

11. GitHub's own large-files guidance explicitly recommends Releases for binaries: "Use GitHub releases to distribute large binaries — no total size or bandwidth limits, but each file must fit your plan's Git LFS limit." Source: https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github

### Upstream distribution channels

12. ryanoasis/nerd-fonts GitHub Releases are the canonical channel. Latest release observed: v3.5.1 (2026-08-21) with 146 assets: one `<Family>.zip` and one `<Family>.tar.xz` per patched family (e.g. `JetBrainsMono.zip`, `CascadiaCode.zip`, `Meslo.zip`), plus `FontPatcher.zip` and a release-wide `SHA-256.txt` checksum file (the release notes state the zip and tar.xz have identical contents). URL shape `https://github.com/ryanoasis/nerd-fonts/releases/download/v3.5.1/JetBrainsMono.zip` is tag-pinned and stable. Source: GitHub API, `repos/ryanoasis/nerd-fonts/releases/latest` (2026-10-10).

13. Maple Mono (subframe7536/maple-font, OFL-1.1) publishes its full variant matrix itself: v7.9 has 88 assets covering `{MapleMono, NL, Normal, NormalNL} × {TTF, TTF-AutoHint, OTF, Variable, Woff2, NF, CN, NF-CN, unhinted}` with a `.sha256` sidecar per zip. `NF` = Nerd-Font patched, `CN` = "Chinese version, embed with Chinese and Japanese glyphs". This means FontAlloy can fetch an already-NF-patched, already-CJK-extended Maple from one origin with published checksums, no patching of its own. Sources: GitHub API `repos/subframe7536/maple-font/releases/latest`; readme at https://github.com/subframe7536/maple-font

14. LXGW WenKai (lxgw/LxgwWenKai, OFL-1.1) and LXGW WenKai Screen (lxgw/LxgwWenKai-Screen, OFL-1.1) publish bare TTFs as release assets (v1.522: `LXGWWenKai-{Light,Regular,Medium}.ttf`, `LXGWWenKaiMono-*.ttf`; Screen repo: `LXGWWenKaiScreen.ttf` etc. — no checksums published, so a fetch script must pin its own sha256 values). Sources: GitHub API `repos/lxgw/LxgwWenKai/releases/latest`, `repos/lxgw/LxgwWenKai-Screen/releases/latest`.

15. Noto CJK (notofonts/noto-cjk) publishes numbered per-configuration zips per major version line (observed tags: `Sans2.004`, `Serif2.003`; assets like `09_NotoSerifCJKsc.zip`, `14_NotoSerifSC.zip`, `01_NotoSerifCJK.ttc.zip`), i.e. per-region OTF subsets and full OTCs are both available tag-pinned. The google/fonts repo mirrors the Google-Fonts-sliced versions as individual files with `OFL.txt` and `METADATA.pb` per family (verified: `ofl/notosanssc/NotoSansSC[wght].ttf`), clonable/pinnable by commit SHA. Sources: GitHub API `repos/notofonts/noto-cjk/releases`, `repos/google/fonts/contents/ofl/notosanssc`.

16. The Google Fonts CSS API (`https://fonts.googleapis.com/css2?family=<spec>`, no API key required) serves subsetted woff2 with `text=` subsetting that can "reduce the size of the font file by up to 90%". The documentation gives no stability or pinning guarantee for the returned `fonts.gstatic.com` URLs, and the served artifacts are subsets/variable instances — not the full TTFs the merge pipeline needs. Usable for web previews, not suitable as the fetch script's source of truth. Source: https://developers.google.com/fonts/docs/css2

### Licensing for redistribution

17. OFL 1.1 permission: anyone receiving a copy may "use, study, copy, merge, embed, modify, redistribute, and sell modified and unmodified copies" subject to conditions; the preamble confirms fonts "can be bundled, embedded, redistributed and/or sold with any software provided that any reserved names are not used by derivative works". Conditions: each copy must include the copyright and license ("as text files, human-readable headers, or machine-readable metadata fields"); no standalone selling of the font; no Modified Version may use the Reserved Font Name(s); the font "modified or unmodified, in part or in whole, must be distributed entirely under this license". Shipping unmodified OFL fonts inside an installer or downloading them at runtime is unambiguously permitted; the obligations are notice-carrying and RFN compliance. Source: https://openfontlicense.org/open-font-license-official-text/

18. LXGW WenKai's OFL is a critical special case: it reserves font names '霞鹜', '霞鶩', '落霞孤鹜', '落霞孤鶩' and 'LXGW', with an additional permission allowing those names only in modified versions "recompiled from the Original Version, without modifications to the font source code" or subsetted/web-converted for web delivery — explicitly not for "installable desktop fonts". FontAlloy's merged output fonts are Modified Versions distributed as installable desktop fonts, so they must not carry the LXGW/霞鹜 names (bundling the unmodified originals for preview is unaffected). Source: https://raw.githubusercontent.com/lxgw/LxgwWenKai/main/OFL.txt

19. Nerd Fonts licensing, in the project's own words: "Nerd Fonts source fonts, patched fonts, and folders with explicit OFL SIL files are licensed under SIL OPEN FONT LICENSE Version 1.1"; the patcher/scripts are MIT; per-font SPDX data is machine-readable in `fonts.json` and `license-audit.md`. Upstream licenses are NOT uniform — the audit table shows BSD-3-Clause (IBM 3270), Apache-2.0 (Droid Sans Mono), Bitstream-Vera (rename requirement), CC-BY-SA-4.0 (BigBlue Terminal — share-alike), Ubuntu Font License 1.0 (naming rules on modified versions), WTFPL, and per-font RFN flags (e.g. Anonymous Pro, Cascadia, D2Coding, IBM Plex Mono, iA Writer, Intel One Mono are OFL-1.1-RFN). Redistribution of the patched fonts is permitted by these licenses, but per-font license files must travel with them, and RFN fonts constrain the naming of merged outputs. Sources: https://raw.githubusercontent.com/ryanoasis/nerd-fonts/master/LICENSE and https://raw.githubusercontent.com/ryanoasis/nerd-fonts/master/license-audit.md

20. Fonts that are NOT redistribution-friendly exist and are systematically excluded by comparable projects: nerd-fonts lists fonts "not included in Nerd Fonts due to their license (proprietary, commercial, etc.)", and programmingfonts.org documents omitting commercial fonts such as Berkeley Mono and PragmataPro. Any FontAlloy catalog must carry per-family license metadata and must not add proprietary fonts. Sources: https://github.com/ryanoasis/nerd-fonts (readme), https://github.com/braver/programmingfonts (readme).

### Precedents

21. fontGoggles (justvanrossum/fontgoggles, Apache-2.0, macOS font viewer) bundles no font binaries at all; it loads user fonts from disk ("drop some fonts onto the app") and auto-reloads on file change. Pattern: pure viewer over user files. Source: https://github.com/justvanrossum/fontgoggles

22. programmingfonts.org (braver/programmingfonts, MIT) commits the font binaries to the repo — but only `.woff2`, "only 4 variants (if available): regular, italic, bold, bold+italic" served from the site's own gh-pages hosting, and requires each font directory to include its license file "exactly as shipped by the creator". Pattern: commit only when artifacts are heavily downsized web subsets with per-font license files. Source: https://github.com/braver/programmingfonts

23. nerdfonts.com routes downloads through GitHub Releases — e.g. its "Download Patcher" button links directly to `github.com/ryanoasis/nerd-fonts/releases/latest/download/FontPatcher.zip`, and the site advertises "72+ patched and ready to use programming fonts" fetched from releases. Source: https://www.nerdfonts.com/ and https://github.com/ryanoasis/nerd-fonts/releases/latest

24. Maple Mono itself is the closest precedent to FontAlloy's catalog problem: one project shipping an entire variant matrix (Mono × NF × CN × formats) as GitHub Release zips with `.sha256` sidecars, consumed downstream by Scoop/Homebrew/AUR/Nixpkgs. Pattern: release-hosted, checksummed, variant-addressable binaries; nothing in git. Source: https://github.com/subframe7536/maple-font and its release assets (finding 13).

25. Repo state: FontAlloy's `.gitignore` already excludes `*.ttf`, `*.otf`, `*.ttc`, `*.woff`, `*.woff2` with the comment "this repo ships the tool, not fonts" — the existing intent is binary-free git. Source: `.gitignore` at repo root.

## Recommendation

### (a) Repo strategy — gitignored binaries + versioned manifest + fetch script + notices; publish a consolidated catalog on GitHub Releases

Keep the repo binary-free (`.gitignore` already does this; findings 8, 25). Build the catalog as data, not as files:

1. **Manifest** (`assets/fonts.manifest.json` or similar, committed): one entry per artifact with `family`, `variant`, `file`, `version` (upstream tag, e.g. `nerd-fonts v3.5.1`, `maple-font v7.9`, `LxgwWenKai v1.522`, `noto-cjk Sans2.004`), `upstream_url` (tag-pinned `releases/download/...` — findings 12–15), `sha256` (from upstream `SHA-256.txt` / `.sha256` where published; computed and pinned by us where not, as for LXGW — finding 14), `license_spdx`, `rfn` flag, and `license_file` reference. This is the single source of truth shared by CLI, GUI, and CI.
2. **Fetch script** (Python, part of `core`/`cli`, e.g. `fontalloy assets fetch`): downloads into a gitignored `assets/fonts/` directory, verifies every sha256, extracts the needed TTF/OTF faces, and fails loudly on mismatch. Developers and CI run it; end users never see git.
3. **THIRD-PARTY-NOTICES.md**, generated from the manifest: per-family copyright line + license text (OFL condition 1 requires the copyright and license to accompany each copy — findings 17, 19). Include RFN notes for merged-output naming (findings 18–19).
4. **CI catalog release**: a GitHub Actions job runs the fetch, repackages per-family zips + a `SHA256SUMS` file, and attaches them to a dedicated release (e.g. tag `font-catalog-v1`, updated as `font-catalog-v2`). Releases have no total-size or bandwidth metering and a 2 GiB per-file / 1000-asset ceiling we never approach (findings 10–11). This gives the runtime one origin under FontAlloy's control instead of four upstreams, while the manifest still records upstream provenance. Model the packaging on Maple Mono's release layout (finding 24).
5. **Rejected alternatives**: Git LFS — metered bandwidth billed against the repo owner on every clone, hard-blocked at $0 budget, ~27 clones/month exhausts the free tier (finding 9). Direct commits — permanent history bloat against documented repo-size guidance (finding 8). Submodules — upstream repos are multi-GB with full history and their tags move independently; the manifest pins equivalents without the clone cost.

### (b) Runtime strategy — bundle a small default set as Tauri resources; download the rest on demand into appDataDir; load everything through the existing FontFace path

Two tiers, one rendering path:

1. **Tier 0 (offline out-of-box)**: bundle a minimal default set — e.g. JetBrainsMono NF (base candidate) + MapleMono-NF-CN (donor candidate), on the order of 20–40 MB — via `bundle.resources` using the map form to control target paths (findings 1–2). The preview grid works on first launch with zero network.
2. **Tier 1 (full catalog, on demand)**: the remaining ~79 families download per-family into `appDataDir()` (writable on all platforms, unlike `$RESOURCES` on macOS/Linux — finding 3), driven by the same manifest, fetched from the FontAlloy catalog release with upstream URLs as fallback, sha256-verified, resumable, with a progress UI. Per-family granularity means the user downloads what they preview.
3. **Rendering**: read the font file as bytes and register with the FontFace API (`new FontFace(name, arrayBuffer)`), exactly the path the validated prototype already uses for user-local fonts. For bundled fonts use `readFile(path, { baseDir: BaseDirectory.Resources })` with `fs:allow-resource-read-recursive`; for downloaded fonts use `BaseDirectory.AppData` with a scoped allow entry (findings 3). This needs no asset-protocol scope, no CSP changes, and no Content-Type assumptions (findings 4–6).
4. **Sidecar**: the fontTools pipeline reads the same files from their `resourceDir()`/`appDataDir` paths — one storage layout serves both webview preview and merging (finding 2).
5. **Do not bundle all 375 MB**: it multiplies installer and update payload for data most users never open (finding 7), while per-family download preserves the "preview quality is the product" experience — the default pair guarantees a non-empty first run, and the full catalog is one click away. `convertFileSrc` remains a documented option for CSS-URL use if ever needed (findings 4–5).

## Open questions

1. Exact Tier-0 default set: which 2–4 families best demonstrate the flagship merge (JetBrains Mono NF + Maple Mono NF-CN is the working assumption; LXGW WenKai Screen vs. non-Screen for CJK donor default).
2. Whether the catalog release should also carry woff2 previews (faster webview registration, but the core needs TTF/OTF anyway; single-artifact-per-face is simpler and matches finding 16's conclusion that the CSS API is not a source of truth).
3. Rate-limit/latency behavior of `github.com/.../releases/download/...` at scale and in mainland China — the endpoints are CDN-backed and unmetered (finding 10), but GitHub documents no availability guarantee for them; a mirror (Gitee for LXGW already maintains one, or a jsDelivr-style CDN fronting the release assets) may be needed if the app grows.
4. Per-family license audit for the 71 NF families: which non-OFL entries (CC-BY-SA-4.0 BigBlue Terminal, Ubuntu Font License, Bitstream-Vera rename rule — finding 19) stay in the catalog, and what their share-alike/rename terms mean for merged outputs built from them; the manifest's `license_spdx`+`rfn` fields exist to force this decision per family.
5. Whether user-facing font metadata (family display names, coverage counts for the preset system) should also live in the manifest or be derived from the fonts at load time.
