# PyInstaller worker-process spawning

Research date: 2026-11-17. Scope: how FontAlloy's packaged serve (PyInstaller onefile wrapping a Click CLI) should spawn its quota'd scan workers, after `[sys.executable, "-m", "fontalloy_core.font_worker", job.json]` was shown to die with exit 2 ("No such option: -m") in the frozen exe while working under source runs. All evidence below is from primary sources: PyInstaller's own docs and changelog, the PyInstaller bootloader C source, CPython stdlib docs, Microsoft Win32 docs, and the source code of three shipped applications.

## Question

What is the established pattern for a PyInstaller-frozen (onefile, Windows/macOS/Linux) Python application to spawn job-runner child processes of itself — given our contract: worker takes one argv (a JSON job path), writes result files, must sit under an OS memory quota (Windows Job Object commit limit / POSIX `RLIMIT_AS`), and must never outlive the serve?

## Findings

### What `sys.executable` is in a frozen app

1. In a frozen app `sys.executable` is NOT a Python interpreter: "When a normal Python script runs, `sys.executable` is the path to the program that was executed, namely, the Python interpreter. In a frozen app, `sys.executable` is also the path to the program that was executed, but that is not Python; it is the bootloader in either the one-file app or the executable in the one-folder app." `sys.argv[0]` is merely "the name or relative path that was used in the user's command." This is why `-m` cannot work frozen: the argument lands in argv of our own Click entry point. Source: https://pyinstaller.org/en/stable/runtime-information.html (same text in `doc/runtime-information.rst` in the PyInstaller repo, lines 136–141).
2. Our exact failure is a documented outcome, not an exotic bug: when a frozen app re-invokes itself without special handling, either an endless recursive spawn loop happens, or "if you have command-line parsing implemented in your program code, the command-line parser raises an error about unrecognized parameters." Click raising `No such option: -m` with exit 2 is the second outcome verbatim. Source: https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html (Multi-processing section; same text in `doc/common-issues-and-pitfalls.rst` in the repo).
3. The frozen app has no interpreter to delegate to at all: "The PyInstaller-frozen application does not have access to python interpreter executable (`python` or `python.exe`) and its environment, and must therefore use its embedded python interpreter. Therefore, any other alternative python-based multi-processing solution would also need to spawn its worker subprocesses using the program executable (`sys.executable`)." Source: same page, "What about other multi-processing frameworks?" section.

### The `multiprocessing` + `freeze_support()` path

4. The only officially supported multi-processing framework is stdlib `multiprocessing`, and it requires calling `multiprocessing.freeze_support()` first — PyInstaller ships a custom override that "is required to be called on all platforms" (unlike the stdlib version, which caters only to Windows). It works by inspecting `sys.argv`: multiprocessing spawns children via `sys.executable`, and in a frozen app the child is invoked as e.g. `my_program.exe --multiprocessing-fork parent_pid=8752 pipe_handle=1552`; `freeze_support()` recognizes those arguments and diverts program flow into the multiprocessing machinery instead of the main program. Symptom of omitting it: "an endless spawn loop of your application process." Source: https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html
5. CPython's own guidance agrees on mechanics: `freeze_support()` must be called "straight after the `if __name__ == '__main__'` line of the main module" (tested with "py2exe, PyInstaller and cx_Freeze"); it has no effect under non-spawn start methods and when running unfrozen. Spawn "starts a fresh Python interpreter process" and is slow compared to fork; the `__main__` module must be importable by children. CPython also warns that spawn/forkserver "generally cannot be used with 'frozen' executables ... on POSIX systems" — PyInstaller's override is what makes spawn work in its frozen apps. Source: https://docs.python.org/3/library/multiprocessing.html
6. Fit for our worker contract: poor. `multiprocessing.Process`/`Pool` replace the argv + job-file + result-files contract with a pickle/pipe protocol and a Python target callable; the entry script's top level re-executes in each worker (the docs devote a section to placing `freeze_support()` before heavy imports so workers are not slowed by them); and the OS quota hooks we rely on disappear — `multiprocessing` on Windows offers no `creationflags`/Job-Object seam (you would assign the job after the fact via `pid`, reintroducing a race), and on POSIX it exposes no `preexec_fn` equivalent for `RLIMIT_AS`. A breach would have to be caught by polling (`tracemalloc`/RSS), which our own `core/fontalloy_core/quota.py` module docstring already rejects as the incident machine's failure mode.

### The re-entry sentinel-argument pattern

7. For anything that spawns workers itself (as we do, via `subprocess`), the official docs prescribe exactly the sentinel pattern: "you would need to implement inspection of program arguments (`sys.argv`), detect attempts at spawning worker subprocesses based on the arguments, and divert the program flow into corresponding framework's function instead of letting it reach your main program code." This is stated as the required approach for every framework that is not stdlib `multiprocessing` — which our `subprocess`-based worker is. Source: https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html ("What about other multi-processing frameworks?")
8. Real-world example 1 — Tribler (PyInstaller-frozen Windows/macOS builds): the GUI process spawns its backend as a second copy of the same exe with a `--core` sentinel: `core_args = sys.argv + ['--core']`, then in frozen builds `core_args = core_args[1:]` ("remove duplicate tribler.exe from core_args when running complied binary", with a comment linking PyInstaller's runtime-information docs), and finally `self.core_process.start(sys.executable, core_args)`. Source: `src/tribler/gui/core_manager.py` lines 121–132 at https://github.com/Tribler/tribler/blob/v7.14.0/src/tribler/gui/core_manager.py
9. Real-world example 2 — qutebrowser (PyInstaller onefile Windows builds): restart re-invokes the frozen exe — `args = [sys.executable]` when `hasattr(sys, 'frozen')`, versus `[sys.executable, '-m', 'qutebrowser']` from source (the exact source/frozen split we need) — and, because the new process must OUTLIVE the current one, sets `env["PYINSTALLER_RESET_ENVIRONMENT"] = "1"` before `subprocess.Popen(args, env=env)`, citing PyInstaller's docs. Source: `qutebrowser/misc/quitter.py` lines 99–106 and 181–191 at https://github.com/qutebrowser/qutebrowser/blob/main/qutebrowser/misc/quitter.py
10. Real-world example 3 — calibre (frozen with its own freezer): job workers are re-invocations of a frozen executable with a `--pipe-worker` sentinel: `p = subprocess.Popen(cmd + ['--pipe-worker', command], **args)`, with the entry point passed via env (`CALIBRE_SIMPLE_WORKER=calibre.utils.ipc.simple_worker:<func>`); under source runs the same code uses `[sys.executable, run-calibre-worker.py]`. Sources: `src/calibre/utils/ipc/simple_worker.py` (https://github.com/kovidgoyal/calibre/blob/master/src/calibre/utils/ipc/simple_worker.py) and `src/calibre/utils/ipc/launch.py` (https://github.com/kovidgoyal/calibre/blob/master/src/calibre/utils/ipc/launch.py).

### Onefile trade-offs and the 6.10 "worker sub-process" mechanism

11. Onefile basics: every start of a onefile binary "creates a temporary folder" `_MEIxxxxxx` and unpacks into it before running; "the single executable is a little slower to start up than the one-folder bundle"; simultaneous copies each get their own folder and "won't interfere with each other" but "running multiple copies is expensive in disk space because nothing is shared"; a killed/crashed process leaves its `_MEI` folder behind; and the docs advise: "Before you attempt to bundle to one file, make sure your app works correctly when bundled to one folder." Source: https://pyinstaller.org/en/stable/operating-mode.html
12. Since PyInstaller 6.10.0, child processes spawned via `sys.executable` are first-class "worker sub-processes": the bootloader now assumes a process spawned from the same executable "is some sort of a worker subprocess that can reuse the already-unpacked resources" (tracked via the `_PYI_ARCHIVE_FILE` environment variable; the old `_MEIPASS2` was renamed `_PYI_APPLICATION_HOME_DIR`). "This means that no additional action is needed to spawn worker sub-processes via `sys.executable`" — no re-extraction per worker. Only processes meant to outlive the parent (restart scenario) must set `PYINSTALLER_RESET_ENVIRONMENT=1`, which is "considered the official and preferred approach at spawning new independent instances of the same application." Sources: CHANGES.rst 6.10.0 (2024-08-10), https://github.com/pyinstaller/pyinstaller/blob/develop/doc/CHANGES.rst; and https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html ("Using `sys.executable` to spawn subprocesses that outlive the application process"). (The docs page's `versionchanged` marker says 6.9, but the changelog places the feature in 6.10.0 — trust the changelog.)
13. Bootloader source confirms the process shape: a top-level onefile start is always split into a parent (bootloader, creates the `_MEI` dir) plus a child (the application) — "the application process is spawned from a parent process that performs the cleanup of the application's temporary files" — whereas a worker sub-process inherits the temp dir (`create_temp_dir = false; /* inherit */`) and runs the application code in that same process, with no second split. So under 6.10+ the PID our `Popen` returns for a re-invoked worker IS the Python worker process. Sources: `bootloader/src/pyi_main.c` in the PyInstaller repo (process-level dispatch around lines 313–395 and 877–881, https://github.com/pyinstaller/pyinstaller/blob/develop/bootloader/src/pyi_main.c) and the "outlive" docs section above.
14. Splash screens (we ship none) are additionally "automatically suppressed in worker sub-processes spawned via `sys.executable`" since 6.10.0. Source: CHANGES.rst 6.10.0, same link as finding 12.

### Windows Job Objects and the re-invoked frozen exe

15. Job Objects apply to a re-invoked frozen exe child like to any process: "After a process is associated with a job, by default any child processes it creates using CreateProcess are also associated with the job" (unless breakaway limits are set); "the association cannot be broken"; a process may belong to multiple jobs — "The ability to nest jobs was added in Windows 8 and Windows Server 2012" (before that, a second `AssignProcessToJobObject` on an already-jobbed process fails); and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` means "closing the last job object handle terminates all associated processes." Nothing in PyInstaller's docs or changelog imposes any Job-Object-specific constraint on its executables. Source: https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects
16. Derived constraint 1 — cover the right process: our `_windows_job_for` (quota.py) assigns the job to the freshly spawned PID. Under the 6.10+ worker mechanism the worker sub-process is a single process (finding 13), so the commit limit binds the real Python worker directly. But if the child ever runs as an independent onefile instance (PyInstaller < 6.10, `PYINSTALLER_RESET_ENVIRONMENT` set, or a different executable path), the spawned PID is only the bootloader parent, and the inner application child is inside the job ONLY if created after `AssignProcessToJobObject` — an unpack-then-spawn race that our assign-immediately-after-`Popen` wins in practice (the bootloader unpacks megabytes first) but which is not guaranteed; the airtight form is `CREATE_SUSPENDED` + assign + resume. Sources: finding 13 (process model) and finding 15 (child inheritance rule).
17. Derived constraint 2 — spawn the exe directly, no shim: PyInstaller 6.22.1 added security validation (GHSA-9fxf-4qw3-ghmr) under which "the bootloader now attempts to look up the parent process ID, and resolve its executable. The path to the parent process' executable must match that of the current process' executable, otherwise an error is raised" for child onefile processes, i.e. worker sub-processes included. Wrapping the spawn in an intermediate process (shell, shim, `cmd /c`) breaks worker-subprocess detection and now fails validation outright. Source: CHANGES.rst 6.22.1 entry, https://github.com/pyinstaller/pyinstaller/blob/develop/doc/CHANGES.rst
18. Hard-killed workers and temp dirs: a worker sub-process owns no `_MEI` directory (it inherits the serve's), so a Job-Object kill of the worker leaks nothing; only an independent onefile instance that is killed leaves a `_MEI` folder behind (finding 11). `KILL_ON_JOB_CLOSE` in our job handle therefore cleans up exactly the worker tree, matching quota.py's "the worker can never be orphaned past its quota" intent.

## Recommendation

### (a) Spawn `[sys.executable, "--worker", job_path]` when frozen; keep `-m` for source runs

Keep `run_worker()` in `core/fontalloy_core/quota.py` exactly as designed (JSON job file in, result files out, OS quota via Job Object / `RLIMIT_AS`, wait + classify) and change only the argv construction at quota.py line 142:

1. **Frozen branch** (`getattr(sys, "frozen", False)`, which PyInstaller sets): spawn `[sys.executable, "--fontalloy-worker", job_json_path]`. `sys.executable` is the bootloader path to this same exe (finding 1), and 6.10+ recognizes the child as a worker sub-process that reuses the serve's already-unpacked `_MEI` directory — no per-worker extraction, no temp-dir churn (findings 12–13).
2. **Source branch**: keep `[sys.executable, "-m", WORKER_MODULE, job_json_path]` unchanged — it is correct when `sys.executable` is a real interpreter (qutebrowser ships exactly this source/frozen split, finding 9).
3. **Dispatch before Click**: in the entry script, check `sys.argv[1:]` for the sentinel first and run the worker loop (import `font_worker`, run, exit) before importing/invoking the Click group — this is the literal mechanism the docs prescribe (finding 7), mirrors `freeze_support()`'s divert-early advice (findings 4–5), keeps worker startup free of Click and any serve-only heavy imports, and cannot collide with user CLI surface as long as the sentinel is not a public option (Click would only see it if we forgot the early check, and then fails loudly with exit 2 as we already observed). A `hidden=True` Click subcommand is a workable alternative but pays Click parse cost per worker and couples the worker to the CLI group; prefer the pre-Click check.
4. **Pin PyInstaller >= 6.10** for packaged builds. If an older PyInstaller must be supported, the same argv still works, but each worker re-extracts and runs as bootloader-parent + application-child — see open risk 2.

### (b) Do not move this worker onto `multiprocessing`

The `freeze_support()` path is the officially supported one only in the narrow sense of stdlib multiprocessing semantics (findings 4–5). Adopting it would trade our file-based job contract for pickle/pipe IPC, re-execute the entry top level per worker, and — decisively — remove the `subprocess.Popen` seams our quota enforcement is built on (`preexec_fn` on POSIX; a well-defined PID to assign the Job Object on Windows), pushing us back toward sampling-based quota observation that quota.py explicitly rejects. Our subprocess design is not an unsupported hack: the docs name argv-inspection re-entry as THE required pattern for anything that is not stdlib multiprocessing (finding 7), and three long-lived shipped applications run it in production (findings 8–10).

### (c) Onefile and the Job Object both stay viable

Onefile remains acceptable for the serve precisely because workers reuse the parent's unpacked dir (finding 12); the per-start extraction cost is paid once per serve launch, not per worker. Onedir would additionally remove the serve's own extraction, its two-process split, and the `_MEI` orphan-on-crash class entirely (finding 11) — a worthwhile packaging simplification if we ever ship installers instead of a single exe, but not required for this fix. For the Job Object: keep the current create-then-assign flow, but note that under 6.10+ the assigned PID is the single worker process (finding 16), and keep the spawn direct (no shell) so 6.22.1's parent-exe validation passes (finding 17).

## Open risks

1. PyInstaller version drift: the worker-reuse semantics and single-process worker shape come from 6.10.0 (docs marker says 6.9, changelog says 6.10.0 — trust the changelog); verify the version pinned in `build/` before relying on temp-dir reuse, and re-test the memory-quota suite against the packaged exe (the current suite evidently ran only source spawns).
2. Pre-6.10 fallback: on older PyInstaller, each worker re-extracts a private `_MEI` dir and splits into bootloader + application processes; the Job Object then caps the bootloader PID and covers the application child only via the create-after-assign inheritance race (finding 16). If we must support old versions, add the `CREATE_SUSPENDED`-assign-resume hardening in `_windows_job_for`.
3. Sentinel hygiene: the sentinel string must never become a public CLI option, and the pre-Click dispatch must run before ANY heavy import; a regression here fails as exit 2 (visible) or as worker slowness (silent). Add one packaged-build test that forces a real (small-quota) breach through the frozen exe.
4. Security-validation interactions: 6.22.1's parent-exe match means the serve must spawn via `sys.executable` directly; any future refactor that wraps worker spawning (shell out, job-object helper process) or drops privileges (the changelog notes privilege-dropping breaks `sys.executable` children) will fail the worker's bootloader validation (finding 17).
5. POSIX specifics: Linux/macOS onefile serves also run parent+child (the serve's own split, finding 13); worker `RLIMIT_AS` via `preexec_fn` is unaffected by freezing, but `preexec_fn` is not async-signal-safe in threaded parents — fine today (the serve spawns from its main flow), worth remembering if spawning ever moves to a thread.
6. `_MEI` orphans remain possible for the serve itself if it is hard-killed (finding 11); unrelated to the worker fix, but a periodic `_MEI` sweep in the serve startup is cheap insurance.
